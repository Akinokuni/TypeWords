# 05 · 本地与服务器双向同步

> 同步机制的设计说明：写入以「操作（Operation）」为单位提交，服务端以单调修订号（revision）
> 做按实体的乐观并发，浏览器端持有离线队列与影子副本，并通过 SSE 接收变更通知。
> 变更历史由 Git 记录，本文只描述当前实现。

## 一、机制概览

```
浏览器 (Pinia store)                        外部 Agent
   │ dispatch(op)：本地乐观应用                │ POST /api/ops
   │ outbox(IndexedDB) + 影子副本              │ （语义化端点 known/collect/note 亦经由同一通道）
   └──────────────► shared/domain/applyOperation.ts ◄──────────────┘
                    唯一的领域逻辑（纯函数，双端共用同一份实现）
                              │
                     Nitro server + SQLite
        store(value/revision) · oplog · meta(revision, replace_revision) · withTransaction
                              │
                     SSE 广播 { scope, revision, count }
```

四层职责：

| 层 | 职责 |
|---|---|
| `shared/domain/applyOperation.ts` | 唯一的状态变更入口；浏览器端与 Nitro 都调用它，保证同一操作在两端结果一致 |
| `server/utils/commitOps.ts` | 服务端唯一写入通道：一个 SQLite 事务内完成幂等校验、乐观并发校验、应用操作、递增 revision、写 oplog |
| `app/core/composables/useOpsSync.ts` | 客户端同步引擎：本地乐观应用、队列投递、增量拉取、SSE 订阅、冲突分流 |
| `app/core/utils/offlineOutbox.ts` | IndexedDB 中的操作队列、影子副本与同步游标 |

## 二、数据结构

### 2.1 服务端（`server/utils/db.ts`）

```sql
CREATE TABLE store (key TEXT PRIMARY KEY, value TEXT NOT NULL, updated_at TEXT NOT NULL);
CREATE TABLE meta  (id INTEGER PRIMARY KEY CHECK (id = 1),
                    revision INTEGER NOT NULL DEFAULT 0,
                    replace_revision INTEGER NOT NULL DEFAULT 0);
CREATE TABLE oplog (revision INTEGER PRIMARY KEY, op_id TEXT NOT NULL UNIQUE, kind TEXT NOT NULL,
                    payload TEXT, entity_keys TEXT NOT NULL, origin TEXT NOT NULL,
                    client_ts TEXT, applied_at TEXT NOT NULL);
PRAGMA journal_mode = WAL;  PRAGMA synchronous = NORMAL;
```

- `store.key` 取值：`dict`、`setting`、`practice_word`、`practice_article`、`practice_sentence`。
- `dict` / `setting` 的 value 是信封 `{ val, version, revision, updated_at }`；练习缓存是 `{ version, val, updated_at }`。
- `meta.revision` 是全局单调修订号，`meta.replace_revision` 记录最近一次整文档替换时的修订号（见 3.3）。
- `oplog` 承担三件事：增量拉取的来源（`?since=`）、opId 幂等去重的依据、变更审计。

### 2.2 操作（`shared/types/ops.ts`）

```ts
interface Operation {
  opId: string          // 全局唯一，重复提交按幂等处理
  kind: OperationKind   // 见 2.3
  payload: object
  clientTs: string
  baseRevision: number  // 提交方看到的最后修订号，用于乐观并发校验
  origin: 'browser' | 'agent' | 'import' | 'server'
  entityKeys: string[]  // 冲突域，由 deriveEntityKeys 推导
  force?: boolean       // 仅用于显式覆盖单调值（进度回退）
}
```

| 冲突域（entityKeys） | 来源 |
|---|---|
| `word:<小写单词>` | `word.*` 各类操作 |
| `dict:<list>:<dictKey>` | 词书进度 / 配置 / 元信息 / 统计 / 增删 |
| `dict:<list>:<dictKey>:content` | `dict.content.replace` |
| `study:<list>` | `study.index.set` |
| `setting:<字段>` | `setting.patch`（逐字段） |
| `practice:<key>` | `practice.session.set` |
| `*` | `doc.replace`（整文档替换） |

两个操作只有在冲突域相交时才互相影响；`*` 与任何键相交。

### 2.3 操作类型

| kind | payload | 副作用与约束 |
|---|---|---|
| `word.known.set` | `{word, value, full?}` | `value=true` 时同时把词移出错词本 |
| `word.collect.set` | `{word, value, full?}` | 收藏集合成员增删 |
| `word.wrong.add` / `word.wrong.remove` | `{word, full?}` / `{word}` | 错词集合成员增删 |
| `word.note.set` | `{word, note}` | 空字符串即删除；key 统一小写，并清理大小写不一致的残留 key |
| `word.fsrs.set` | `{word, card}` | 内容一致时不产生变更 |
| `word.fsrs.remove` | `{word}` | 删除记忆曲线卡片 |
| `dict.progress.set` | `{list?, dictKey, lastLearnIndex?, complete?}` | 进度默认只增不回退；`force: true` 允许显式回退 |
| `dict.config.set` | `{list?, dictKey, patch}` | 每日词量等配置字段 |
| `dict.meta.set` | `{list?, dictKey, patch}` | 名称 / 描述 / 封面 |
| `dict.statistics.push` | `{list?, dictKey, entries[]}` | 按 `id`（缺失时按内容指纹）去重，只增不减 |
| `dict.add` | `{list, dict}` | 已存在同 id 的词书时不产生变更 |
| `dict.remove` | `{list, dictKey}` | 移除词书，并修正学习指针 |
| `dict.content.replace` | `{list, dictKey, words?/articles?}` | 整体替换内容 |
| `study.index.set` | `{list, dictKey}` | 学习指针以 key 表达，两端各自解析为下标 |
| `article.collect.set` | `{articleId, value, full?}` | 文章收藏 |
| `setting.patch` | 字段平铺 | `scope` 必须为 `setting` |
| `practice.session.set` / `doc.replace` | 由服务端产生 | 通知类记录，客户端不提交 |

`list` 缺省为 `word`，可选 `article`。`payload.full` 用于携带完整 Word 对象（列表展示需要释义）。

### 2.4 浏览器端本地存储（`app/core/utils/offlineOutbox.ts`）

| IndexedDB key | 内容 |
|---|---|
| `typewords-outbox` | 待提交操作队列；同实体同类型的可折叠操作就地替换，队列有界 |
| `typewords-shadow-<scope>` | 影子副本：最后一次成功读到的服务端文档，供离线启动 |
| `typewords-sync-meta` | 每个 scope 的 `{ revision, updatedAt, lastSyncedAt }` 与设备标识 |

## 三、服务端写入路径

`commitOperations(stateKey, ops)` 在 `BEGIN IMMEDIATE` 事务内按顺序处理每条操作：

1. **scope 校验**：`scopeOfOperation(kind)` 与 `stateKey` 不一致时拒绝该操作（`INVALID_PAYLOAD`），
   避免把设置补丁写进词典文档。
2. **幂等**：`op_id` 在当前文档代内已存在时直接回带原 revision，不重复应用。
3. **乐观并发**：当 `baseRevision` 小于本批次开始时的 revision，且区间 `(baseRevision, startRevision]`
   内存在冲突域相交的既有操作时，该操作记入 `conflicts[]` 并跳过；冲突域不相交则直接应用。
4. **应用**：调用与浏览器端同一份 `applyOperation`。
5. **记账**：仅当 `changed=true` 才写入 `oplog` 并递增 revision；本批次只要有变更，最后一次性写回文档与 `meta.revision`。

### 3.1 幂等与重放

重复提交同一 `opId` 不产生第二次变更，因此网络重试与离线重放是安全的。
状态已一致的操作返回 `changed=false`，同样不写日志、不推进 revision。

### 3.2 按实体的并发

冲突判定的粒度是操作影响的实体键。因此「Agent 批量标记单词」与「用户练习另一本词书」互不阻塞；
同一单词被两端同时修改时才会产生冲突，由客户端决定自动重试还是交给用户选边。

### 3.3 文档代（generation）

整文档替换（导入 / 历史快照恢复 / 手动覆盖）会把文档整体换掉，此时先前的应用记录不能作为
「该意图已生效」的依据——否则响应丢失后重试的操作会被幂等去重跳过，而替换后的文档里并不包含它。
`meta.replace_revision` 记录最近一次整文档替换的修订号，`findAppliedOpRevision` 只认晚于它的记录；
同一个 opId 再次落库时以 `ON CONFLICT(op_id) DO UPDATE` 推进到新 revision。

### 3.4 整文档替换与练习会话

- `replaceDocument(stateKey, envelope, origin, label)`：写入整份文档，写一条 `doc.replace`，
  递增 revision 并设置 `replace_revision`。`PUT /api/data/dict|setting` 经此路径。
- `bumpPracticeSession(key, updatedAt)`：练习快照体积大，不进 oplog 的 payload；
  仅递增 revision 并写一条 `practice.session.set` 通知，客户端据此重新拉取。

## 四、HTTP 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/ops` | `{ scope, ops[] }` → `{ revision, applied[], conflicts[] }`；有变更时广播 SSE |
| GET | `/api/ops?since=<revision>` | `{ revision, mode, ops[] }`；`mode="snapshot-required"` 表示落后超过 500 条 |
| GET | `/api/ops/stream` | SSE；变更通知 `{"scope","revision","count"}`，25s 心跳 `ping` |
| GET | `/api/data/:key` | `{ value, revision?, updatedAt }`；`value=null` 表示服务端确认无数据 |
| PUT | `/api/data/:key` | 整文档替换；练习缓存按信封 `updated_at` 做 LWW，服务端较新时返回 `applied:false` |
| POST | `/api/words/:word/known\|collect\|note` | 语义化写入；内部构造对应操作，返回 `{ changed, revision }` |

响应约定：

```jsonc
// POST /api/ops
{
  "revision": 14,
  "applied": [{ "opId": "...", "revision": 14, "changed": true }],
  "conflicts": [{
    "opId": "...", "kind": "dict.progress.set", "reason": "ENTITY_MODIFIED",
    "serverRevision": 14, "conflictingOps": [ /* 相交的既有操作 */ ]
  }]
}
```

`reason` 取值：`ENTITY_MODIFIED`（并发冲突）、`INVALID_PAYLOAD`（scope 不匹配或载荷非法）、`UNKNOWN_KIND`。

## 五、客户端同步引擎

`useOpsSync()` 是单例，多个组件取得同一实例（各自维护 revision 会导致互相覆盖）。

| 方法 | 行为 |
|---|---|
| `dispatch(kind, payload?, options?)` | 应用 `applyOperation` → 入 outbox → 合并窗口后提交；`immediate: true` 时等待提交完成 |
| `dispatchMany(ops, options?)` | 一批操作共用同一基准提交（例如一次练习结算） |
| `flush(scope)` | 取该 scope 的操作批量 POST；成功则出队并更新游标，失败保留队列、指数退避、`online` 事件重试 |
| `pull(scope)` | `GET /api/ops?since=<游标>`，过滤本端回环后应用他人操作；遇到 `doc.replace` 或 `snapshot-required` 时全量重载 |
| `subscribe()` | `EventSource('/api/ops/stream')`，收到通知后 200ms 去抖拉取 |
| `pushWholeDocument(scope)` | 整文档写入（导入等无法用操作表达的场景），并登记新 revision |
| `noteDocumentWrite(scope, revision)` | 供整文档写入方调用：推进游标并跳过自触发的全量重载 |

**离线行为**：`base.init()` / `setting.init()` 读服务端失败时使用影子副本启动并置为离线状态，
不写入默认值；`navigator.onLine === false` 时只入队不发请求；恢复连接时先拉增量再推送积压。

**开发期探针**：`app/core/utils/opsBridge.ts` 记录状态指纹，dev 下若检测到未经 `dispatch` 的
dict 写入会打印告警，提示该调用点尚未接入同步通道。

## 六、冲突处理

| 分流 | 操作类型 | 处理 |
|---|---|---|
| 自动合并 | 集合增删、`word.fsrs.*`、`dict.statistics.push`、`article.collect.set` | 先 `pull` 取最新基准，再用新 `baseRevision` 重投（最多 2 次）；reducer 的幂等与单调性保证结果正确 |
| 弹窗选边 | `setting.patch`、`word.note.set`、`dict.progress.set`、`dict.config.set`、`dict.meta.set`、`dict.add/remove`、`dict.content.replace`、`study.index.set` | `SyncConflictDialog` 展示「本机 vs 服务端」：<br>「保留本机」→ 新 `opId` + 当前 `baseRevision` + `force: true` 重投；<br>「采用服务端」→ 丢弃本地这批操作并全量重载 |

只有对应强制操作被服务端接受时才移除原始操作；重投期间再次冲突的操作留在队列等待下次处理。
冲突轮次上限为 3，超过后保留队列并置为冲突状态。

## 七、练习会话缓存

练习会话是整快照语义，不存在有意义的合并，只存在「哪次练习更靠后」：

- 本地 IndexedDB 为主；`restoreIfStale` 按信封 `updated_at` 做 LWW，本地缺失或较旧时恢复服务端快照。
- 上传时机：本地保存后、30s 静止、60s 定时、`visibilitychange` 隐藏、`pagehide`（keepalive 并发发出）。
- 服务端在 `PUT /api/data/:key` 中拒绝较旧的快照（`applied:false`），并广播 `practice.session.set` 通知。
- 练习页据此弹「检测到其他设备的新进度」对话框，由用户决定是否重新加载。

## 八、不变量与已知限制

不变量：

- 同一操作在浏览器端与服务端结果一致（共用 `applyOperation`）。
- 写操作幂等：同 `opId` 重复提交、或状态已一致，都不产生额外变更。
- `changed=false` 的操作不写 oplog、不推进 revision。
- 集合类数据（收藏 / 错词 / 已掌握）内容收敛；学习记录（statistics）只增不减。
- `dict.progress.set` 在没有 `force` 时不会让进度回退。
- 读服务端失败与「服务端确认无数据」是两种结果，只有后者允许写入默认值。

已知限制：

- 集合类数据的数组顺序不保证两端一致（仅内容收敛）。
- 浏览器端交互的自动化用例尚未接入（reducer 有单测，服务端有 HTTP 端到端脚本，浏览器侧依赖手工验证）。
- `doc.replace` 的冲突域是 `*`，导入之后所有基准过期的操作都会进入冲突流程；可按词书细化冲突域以降低弹窗频率。
- 大块导入以整文档替换处理，没有做三路合并。
- `dict` 仍是单行 JSON，`fsrsData` 随学习量增长，单次提交需要读写整份文档；可拆为独立表优化。
- 官方词书的 `words` 不落库（`length` 记录词数），服务端文档中该字段为空属正常。
