# 04 · 认证与安全边界

## 改动目标

纯个人使用，**不做认证/登录**；在保证使用方便的前提下，明确最小安全边界与数据保护措施，并提供**可选**的 `API_TOKEN` 轻量防护。

## 现状

- 无账号体系；数据的权威副本在自带服务端（SQLite），浏览器保留缓存与未提交的操作队列。
- 同步由内置服务端的 `/api/ops*` 承担，不依赖外部数据库服务。

## 方案（建议）

1. **无认证**：后端 API 不引入登录/鉴权中间件；未设置 `API_TOKEN` 时完全无鉴权。
2. **监听地址**：默认仅监听 `127.0.0.1`（本机）；如需内网/外网访问，显式配置 `HOST=0.0.0.0`。
3. **可选 API_TOKEN 防护（已决策采用，默认关闭）**：
   - 环境变量 `API_TOKEN` + 请求头 `Authorization: Bearer <token>` 校验（Agent 配置同一 token）。
   - 反向代理层可再做 IP 白名单。
4. **内部接口的例外（R5 已确认采用「方案 A」）**：
   - `/api/health`、`/api/data/*`、`/api/ops*` 属于**浏览器前端内部接口**，不校验 token
     （浏览器端拿不到 token，而这些接口是应用自身运行所必需）。见 `server/middleware/auth.ts` 注释。
   - 因此**设了 token 也不代表数据写入口被保护**：`/api/ops` 与 `/api/data/*` 都能改数据。
     这是「单机 / 内网个人使用」前提下接受的取舍。
5. **数据保护**：
   - 数据文件在宿主机卷 `./data/`，随容器生命周期持久化。
   - 提供 `/api/export` 手动备份 + 建议定期快照（见 02）。
   - 服务端通过 `oplog` 保留全部变更记录，误操作可据此追溯（但不提供自动回滚）。
6. **风险说明**：无认证意味着「能访问端口者即可读写数据」，因此**不要**直接暴露到公网；
   若必须远程访问，走 SSH 隧道、加 token，或在反代层加 IP 白名单。

## 涉及文件

- `server/middleware/auth.ts`（可选 token 校验 + 内部接口白名单）
- `docker-compose.yml`（监听地址、端口、可选 API_TOKEN 环境变量）
- `app/core/utils/http.ts`（若加 token，前端请求头注入）

## 状态

- 已完成（typecheck + dev / 生产构建运行时验证通过）
- 已决策：提供可选 `API_TOKEN` 轻量防护，默认关闭（未设置 API_TOKEN 时无鉴权）
- 已决策（R5）：内部接口 `/api/data/*`、`/api/ops*` 不纳入 token 校验，前提是**不暴露公网**
