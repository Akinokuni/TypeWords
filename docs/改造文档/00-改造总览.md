# 00 · 改造总览

> 对本次「私人化改造」全部改动需求的**整体概括**。细节见各分项文档（01~04）。

## 一、改造目标（一句话）

把 TypeWords 从「纯前端 + 浏览器本地存储」的静态站点，改造为「前端 + Node 后端 + 服务端存储」的**单机可部署**应用，用 Docker 打包，对外暴露后端 API 供 Agent 读取学习进度、操作数据。纯个人使用，不做认证。

## 二、需求清单

| 编号 | 需求 | 摘要 | 文档 |
|------|------|------|------|
| R1 | Docker 部署 | 容器化打包与运行，数据持久化到宿主机卷 | [01](./01-Docker部署.md) |
| R2 | 存储层迁移到服务端 | 核心数据改为服务端存储，使用 SQLite | [02](./02-服务端存储层.md) |
| R3 | 后端 API + Agent 对接 | 暴露标准 REST API：读进度、写数据，供 Agent 操作 | [03](./03-后端API与Agent对接.md) |
| R4 | 无认证 | 个人场景，不做登录鉴权，可选 API_TOKEN | [04](./04-认证与安全边界.md) |

## 三、现状 vs 目标

| 维度 | 现状 | 目标 |
|------|------|------|
| 运行形态 | 纯前端（浏览器内） | 前端 + Node 后端（同一进程，Nitro server） |
| 部署 | 静态文件托管（Ali OSS / EdgeOne Pages） | Docker 容器（镜像 + compose） |
| 数据存储 | IndexedDB（浏览器本地） | 服务端 SQLite |
| 数据同步 | Supabase（可选，`typewords_data` 表） | 后端 API 直接读写，去掉 Supabase 依赖 |
| 对外接口 | 仅 `public.word/query`（查词） | 标准 REST API（进度/统计/数据操作，附 OpenAPI） |
| 认证 | 无登录，可选 Supabase 账号 | 无认证（个人），可选 API_TOKEN |

## 四、目标架构

```
┌─────────────── Docker 容器 ───────────────┐
│                                            │
│  ┌──────────────────────────────────────┐  │
│  │  Nuxt 应用（前端 SSR + Nitro server）  │  │
│  │                                      │  │
│  │   前端页面  ──HTTP──▶  server/api/*   │  │
│  │                              │        │  │
│  │                              ▼        │  │
│  │              存储层（SQLite）          │  │
│  └──────────────────────────────────────┘  │
│                     │                       │
└─────────────────────┼───────────────────────┘
                      ▼
             宿主机数据卷 ./data（持久化）
                     ▲
                     │ REST API（无认证，默认仅监听本机/内网，可选 API_TOKEN）
                外部 Agent（读进度 / 操作数据）
```

## 五、技术选型建议

| 项 | 建议 | 理由 |
|----|------|------|
| 后端运行时 | Nuxt 自带 **Nitro server**（`server/api/*.ts`） | 前后端同仓库同进程，改动最小，复用现有 TS 类型 |
| 存储引擎 | **SQLite**（`better-sqlite3` 或 Node 内置 `node:sqlite`） | 单文件、零运维、事务与并发够用、易备份 |
| 容器编排 | **多阶段 Dockerfile + docker-compose.yml** | 一命令构建/启动，数据卷挂载持久化 |
| 接口风格 | **标准 REST + JSON**（HTTP 状态码 + 直接资源 JSON）+ OpenAPI | Agent 读取最直接，可自动发现接口 |

> **已定决策**：存储引擎采用 **SQLite**；练习会话缓存保留浏览器本地；API 采用标准 REST + JSON（面向 Agent 易读）并附 OpenAPI；认证采用无认证 + 可选 `API_TOKEN`（默认关闭）。

## 六、改造范围

### A. 前端改动（现有代码）
- 存储读写入口：`app/core/stores/base.ts`、`app/core/stores/setting.ts`、`app/core/composables/useDataSyncPersistence.ts`
- 存储 key / 配置：`app/core/config/env.ts`
- HTTP 层：`app/core/utils/http.ts`、`app/core/apis/words.ts`
- 同步逻辑：`app/core/utils/supabase.ts`（拟移除或改造）
- 练习会话缓存：`app/core/utils/cache.ts`（保留浏览器本地，不迁服务端）

### B. 后端新增
- `server/api/*` —— 数据读写与进度/统计接口（当前项目无 `server/` 目录）
- 存储模块 —— SQLite 数据访问层、建表/迁移脚本
- 数据模型映射 —— 复用 `app/core/types/types.ts` 的 `Dict`/`Word`/`Article`/`Statistics`/`SettingState` 等类型

### C. 部署新增
- `Dockerfile`、`docker-compose.yml`、`.dockerignore`（已存在，需核对）
- 环境变量（端口、数据目录、可选 API_TOKEN 等）

## 七、建议实施顺序

1. **R2 服务端存储**：先让数据能落到服务端（SQLite 数据模型 + 读写 API + 迁移），是后续一切的地基。
2. **R3 API + Agent 对接**：在存储层之上补齐进度/统计/操作接口 + OpenAPI。
3. **R1 Docker 部署**：打包验证，数据卷持久化。
4. **R4 安全边界**：监听地址、可选 API_TOKEN、备份策略收尾。

> 注：R1 与 R2 可并行，但最终联调以「存储先通」为前置。

## 八、风险与注意

- **数据迁移**：现有用户数据在浏览器 IndexedDB 里，需提供一次性导入到服务端的通道（首次启动导出 JSON 再导入）。
- **SSR 与后端耦合**：`app.vue` 等有 `import.meta.client` 分支，迁移时要保证存储逻辑在服务端安全执行。
- **单实例约束**：无认证 + SQLite 单文件，天然单实例、单用户，适合个人场景，不支持多用户并发写入。
- **备份**：SQLite 文件在宿主机卷中，需约定备份策略（见 04）。
